# 0.1.3 HTTPS 握手优化与验收

日期：2026-10-12。

## 结论与范围

在开发机隔离网络中复现了大量持久连接叠加持续传输时的 CPU 开销和握手排队。0.1.3 在相同转发流量下明显降低 CPU 占用和握手尾延迟，保持 TCP/QUIC 分流及现有容量保护。

生产机检查期间未替换正在运行的内核、未重启服务、未修改规则或系统网络参数。线上抽样没有复现异常的内核附加握手延迟，部分路径存在较高 RTT 和重传；不能将所有慢握手归因于程序。本次结果是开发环境可复现负载下的优化证据。

## 实现

- 小连接的每方向 pipe 初始请求容量从 64 KiB 调整为 8 KiB，真实转发达到 256 KiB 后仍尝试扩到 1 MiB。内核按页对齐；扩容失败保留可用容量继续传输。
- 单次 splice 最多处理 256 KiB，每方向累计处理约 256 KiB 后主动让其他任务运行。已有 Tokio 协作调度继续有效；不添加固定延迟，不等待小请求凑满缓冲。
- 维持零复制、TCP_NODELAY、TCP keepalive、双向半关闭和原有错误处理。没有放宽连接数、每 IP、握手并发或内存保护，也没有增加服务权限。

Linux 对普通用户的 pipe 容量有总配额；达到软限额后，新 pipe 容量会变小且扩容被拒绝。依据：[Linux pipe(7)](https://www.man7.org/linux/man-pages/man7/pipe.7.html)。开发机保持原有 16384 页软限额，以普通用户创建 4000 个 pipe 后，旧初始容量策略的新 pipe 扩到 1 MiB 返回 EPERM，实际仅 8 KiB；新策略下可扩到 1 MiB。此次没有通过改全局 sysctl 绕开配额。

## 对比方法与结果

Debian 13，4 CPU、16 GiB 开发机；路由进程仅可使用 1 个 CPU，其余 CPU 运行测试端。独立网络命名空间、回环地址、相同工具链。重新编译的 0.1.2 与生产发行版 SHA256 完全相同。

每轮保留 2000 条连接，16 条持续 HTTP 下载，同时每秒进行 100 次真实、完整、验证夹具证书的 TLS 握手和 HTTP 响应校验。每轮 15 秒，旧版与候选实现交替运行，各做三轮。手动容量模式和 65536 FD 限额用于隔离数据路径性能；自动容量另做真实 cgroup 测试。CPU 为整个负载阶段均值，含建连、预热、收尾；RSS 不含内核内存。

三轮中位数如下。候选转发实现与正式 0.1.3 一致，正式版本号产物另行复测。

| 合计负载 | 指标 | 0.1.2 | 0.1.3 候选 |
| --- | --- | ---: | ---: |
| 4 Gbps | 握手 P95 | 9.31 ms | 5.56 ms |
| 4 Gbps | 握手 P99 | 17.89 ms | 8.56 ms |
| 4 Gbps | 单核 CPU | 60.98% | 29.11% |
| 6 Gbps | 握手 P95 | 31.43 ms | 5.16 ms |
| 6 Gbps | 握手 P99 | 42.10 ms | 8.42 ms |
| 6 Gbps | 单核 CPU | 82.26% | 37.63% |

两组对比共 18000 次握手全部成功，各轮已建立连接的持续心跳、逐条最终通信检查均通过。完整逐轮数据、实际吞吐和管道配额实验见 [原始汇总](https-0.1.3.json)。

最终 amd64 发布产物额外复测：

| 场景 | 成功握手 | 实际吞吐 | 握手 P99 | 单核 CPU |
| --- | ---: | ---: | ---: | ---: |
| 2000 条持久连接，无持续下载 | 1000/1000 | — | 8.21 ms | 10.38% |
| 2000 条持久连接，16 路下载 | 2000/2000 | 6.000 Gbps | 13.05 ms | 34.76% |
| 3500 条持久连接，16 路下载 | 3000/3000 | 4.000 Gbps | 8.53 ms | 45.85% |

以上复测中没有存量连接断开或心跳失败，结束后活动 TCP、待握手和 IP 跟踪项均回到 0。低负载握手 P99 与旧版的约 8.6 ms 相近。

不限速探索中，新实现约 19.39 Gbps、旧版约 6.69 Gbps，但两者流量不同，新实现的端到端握手 P99 约 159 ms，旧版约 78 ms。测试端和回环网络本身也参与竞争，因此不能用该组结果声称饱和极限下握手更快。本次收益是同等负载下减少开销、增加余量；CPU、带宽或链路彻底饱和时仍可能排队。回环吞吐不代表公网带宽或任何机器的保证值。

复现步骤见 [压测夹具说明](../benchmarks/tls-latency/README.md)。

## 功能与安全验收

- Rust 19 项单元测试通过，cargo fmt、Clippy 全目标检查通过。
- HTTP Host、TLS SNI、精确/通配规则、IPv6、QUIC v1/v2、普通 UDP 拒绝、私有控制 socket、事务式热更新及旧连接保持通过。
- 20000 个畸形/随机 UDP 输入、非法 PROXY 输入、自转发循环防护与过期配置事务拒绝通过。
- 丢包、延迟、后端 RST/拒绝、慢连接、半关闭、DNS/DDNS 故障和恢复、MTU 1280、接口下线/恢复测试通过。
- 24 次配置热更新、每代 1801 条规则与持续旧连接检查通过。
- 真实 cgroup 内存和 CPU 压力保护通过：保护时拒绝新流量，既有 TCP/QUIC 保持可用，压力解除后容量恢复。
- 180 秒持续测试完成 110293 次 TCP、27191 次 QUIC 数据交互以及 2293 次重连，失败 0；结束后连接、队列和 IP 跟踪资源全部回收。
- cargo audit 当前锁定依赖：已知漏洞 0、告警 0。本次没有引入运行依赖，没有修改认证、控制 socket 权限或下载信任根。
- Bash 语法与 ShellCheck 通过；构建 amd64/arm64 静态产物，arm64 经 QEMU 验证版本输出及配置校验。性能与完整功能实测使用 amd64，未在真实 ARM 主机做吞吐对比。

## 升级边界

配置格式与规则兼容 0.1.2。规则修改仍可热更新；替换正在运行的旧内核需要重启，现有连接可能重连。需要不中断用户连接时，应先保留旧进程，在允许短暂重连的维护窗口切换。本次生产检查不会为了安装新版主动断开用户连接。
